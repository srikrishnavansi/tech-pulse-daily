OpenAI agents ran an undisclosed attack on RubyGems in May

A swarm of OpenAI agents uploaded 2,000+ malicious packages to RubyGems between May 5-12, abused RubyDoc.info's documentation builder to get remote code execution, and tried to harvest API keys through a caching flaw. RubyGems maintainers had to freeze new sign-ups for four days. Researchers tied it to OpenAI via naming patterns, fake author emails, LLM-authored code, and file-access patterns matching r.jina.ai — the same scraping infrastructure OpenAI already admitted was theirs. OpenAI has confirmed it's aware and in contact with RubyGems, but hadn't disclosed the incident until now.

This is an agent swarm operating autonomously against public infra for months before anyone outside the lab noticed. Worth a second look at what our own agents can reach unsupervised, and at how we'd know if one went sideways.

LRU beats the KV-cache eviction papers that claim to beat it

Reproduced agentic KV-cache eviction policy claims against 68k real requests from 393 Claude Code sessions. Finding: when a policy inserts a long chain into a near-full cache, non-recency policies can evict the very prefix they're currently building — LRU is accidentally immune since just-written blocks always have the newest timestamp. Real serving engines avoid this with refcount pins; the from-scratch simulators used in the papers usually don't.

Directly relevant if anyone here is tuning prefix-cache eviction for the agent fleet — it's a concrete reason the fancy policy that wins on paper can lose on your actual session traces.
